02

Arquitetura de Dados

Projeto-âncora

Plataforma de dados instalável por empresa, com stack open source.

O que é

Uma plataforma de dados instalada por empresa por um script interativo: ingere dados das fontes, transforma, cataloga, serve dashboards em um portal executivo próprio e inclui um agente de IA. Tudo roda em containers, sobre stack open source.

Como é montado

São sete camadas. Ingestão e transformação com Sling e dbt, orquestradas pelo Dagster; catálogo no OpenMetadata; BI no Superset; portal executivo em React e FastAPI, com SSO e RLS por grupo; agente de IA com Dify, LiteLLM e Langfuse; Traefik na borda. Um único Postgres é o datalake.

Por que assim

Montei conjuntos fechados de ferramentas open source, com o volume de dados como principal critério de corte e o Postgres como datalake em todas as variantes. Escolhi o Dagster pela integração nativa com o dbt e pela operação mais leve, e adotei uma única ferramenta de BI, para manter tudo simples.

Decisões de arquitetura

  • Um Postgres, um role e um banco por serviço Todas as stacks usam o mesmo Postgres, mas cada serviço tem role e banco próprios; o role do datalake não é superusuário e não acessa os bancos do Dify, Langfuse e LiteLLM.
  • Instalação por empresa, por um script Cada empresa ganha a própria instalação (portal single-tenant). O script gera os .env sem rotacionar segredos existentes, sobe os serviços na ordem certa e cria os administradores. Virar multi-tenant é uma refatoração conhecida, não uma reescrita.
  • Uma borda compartilhada Um único Traefik é a entrada pública de toda a solução, no lugar de um proxy por stack. O banco nunca fica na rede do proxy.
  • Embedding sem expor credenciais Só o backend fala com o endpoint de guest token do Superset. O frontend recebe um token de curta duração (cerca de 5 minutos), já com o RLS dos grupos do usuário.
  • Superset como única ferramenta de BI Comparei três opções. O Lightdash não oferece embedding na edição open source auto-hospedada; o Superset tem licença Apache, sem recursos travados, com RBAC e RLS maduros.

03

Minha Loja

SaaS web e mobile

SaaS de gestão administrativa para organizações de associados.

O que é

SaaS de gestão administrativa para organizações de associados, com app web e app mobile em paridade de funcionalidades sobre o mesmo backend. Os módulos cobrem associados, financeiro, reuniões e atas, comunicados e cobrança da assinatura.

Como é montado

Monorepo pnpm com web em Next.js e React, mobile em Expo (React Native) e API em Fastify com TypeScript, sobre PostgreSQL com Drizzle. Schemas Zod e design tokens são pacotes compartilhados. O isolamento entre organizações usa uma coluna de tenant em cada tabela de dados de tenant, mais RLS, e a autenticação é própria, com JWT RS256.

Por que assim

Escolhi um backend próprio, e não um BaaS, para ter controle total sobre dados sensíveis e conformidade com a LGPD, e TypeScript de ponta a ponta para compartilhar a validação entre clientes e API. Só a API tem mais de 60 arquivos de teste, incluindo testes de isolamento por RLS.

Decisões de arquitetura

  • Schema compartilhado com coluna de tenant e RLS Toda tabela de dados de tenant tem uma coluna de tenant, e o RLS do PostgreSQL reforça o isolamento como camada extra de defesa. Banco por tenant e schema por tenant foram descartados pelo custo de migração.
  • O tenant vem sempre do JWT O backend injeta o tenant somente a partir das claims do JWT (RS256, token de acesso de 15 minutos), nunca do corpo da requisição.
  • Schemas Zod compartilhados TypeScript de ponta a ponta: os mesmos schemas Zod validam web, mobile e API, sem regras duplicadas. Um único pacote de design tokens serve web e mobile.
  • Permissões em uma matriz declarativa Uma matriz declarativa de permissões, com um ponto de checagem no backend (authorize) e outro nos clientes (usePermission), em vez de condicionais espalhadas.
  • Livro financeiro append-only Lançamentos não têm rotas de alteração nem de exclusão; correções entram como novos lançamentos de crédito ou estorno, preservando a trilha de auditoria.

LOU

App mobile e API

App de bem-estar e relacionamento para casais 35+.

O que é

App mobile de bem-estar e relacionamento para casais 35+, com onboarding, criação de casal por código de convite, conteúdo guiado em áudio e vídeo e notificações push.

Como é montado

App em Expo (React Native, Expo Router), com estado em Zustand e dados do servidor em TanStack Query. API FastAPI com SQLAlchemy assíncrono e Alembic sobre PostgreSQL, com Redis provisionado no Compose. Tudo roda em Docker Compose numa VM Linux, com nginx no stack de produção.

Por que assim

Priorizei time-to-market e custo previsível: Expo gerenciado, FastAPI pela velocidade de desenvolvimento e uma VM com Compose, sem vendor lock-in. O app nasce com quatro locales para atender a região DACH e o Brasil.

Decisões de arquitetura

  • Idiomas desde o primeiro dia Quatro locales (de, pt-BR, de-AT, de-CH), com alemão como padrão, porque refatorar i18n depois custa caro. O texto dos conteúdos fica numa tabela por locale, para permitir mídias diferentes por idioma.
  • Expo no fluxo gerenciado Escolhido pelo time-to-market, para focar no produto em vez de na infraestrutura nativa.
  • VM Linux com Docker Compose, sem serverless Custo previsível, controle total e nenhum vendor lock-in.
  • Agendador dentro da API O APScheduler roda no processo da API em vez de um worker Celery, evitando um container a mais numa VM única. Migrar para Celery é simples se a escala exigir.
  • Isolamento por RLS com role sem dono O isolamento de dados usa Row Level Security no PostgreSQL, e a API conecta com um role que não é dono das tabelas, porque donos ignoram o RLS.

Como eu construo

Método de desenvolvimento assistido por IA, com disciplina de engenharia.

  1. Planejamento por fases

    Cada entrega é dividida em fases. Toda fase segue o mesmo ciclo: pesquisa, mapeamento de padrões, plano, checagem do plano, execução por ondas, verificação e fechamento.

  2. Branches protegidas

    A branch principal é protegida: mudanças entram só por pull request, sem force push nem exclusão. Em um dos projetos há duas branches protegidas, integração e produção, com CI obrigatório e promoção manual.

  3. PR por fase

    Cada fase roda na própria branch e fecha com um pull request, com commits atômicos a cada tarefa. A fase seguinte só começa depois do merge, e o merge é sempre uma decisão humana.

  4. Verificação independente

    Um verificador independente reconfere cada fase ao vivo, sem se apoiar só no resumo de quem executou, e já encontrou lacunas reais de qualidade. Entregas visuais passam por checkpoint humano em navegador real; em uma fase, ele achou 4 bugs que nenhum teste automatizado pegaria.

Verificações adiadas recebem o status formal PASS-WITH-KNOWN-GAP, com a lacuna declarada, em vez de serem dadas como aprovadas. Segredos reais nunca são versionados.
